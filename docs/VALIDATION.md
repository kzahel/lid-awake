# Validation record

## Current result

Version [0.0.5](https://github.com/kzahel/lid-awake/releases/tag/v0.0.5) is a signed and notarized prerelease. A real 0.0.4-to-0.0.5 Sparkle update passed in the machine-control Tart VM, including detection and repair of a stale registered helper. The installed build 5 app and helper passed on/off, forced app exit, helper restart, and unsigned XPC client rejection checks. On a physical Mac, version 0.0.3 sustained a roughly one-hour closed-lid remote session; version 0.0.4's icon remained visible against a black menu bar and its on/off controls changed the observed sleep state. The physical timestamped-heartbeat and normal-sleep lid-close control on version 0.0.5 in [the test plan](TESTING.md) remain open. The Tart VM has SIP disabled, so it does not replace a stock SIP-enabled acceptance test.

## Detailed record

2026-09-27, macOS 26 / Xcode 26.6:

- Debug app and helper compile; all three session policy and I/O Registry parser XCTest tests pass locally.
- Signed Release archive exports as a universal `arm64` + `x86_64` app. The exported app and nested helper pass strict `codesign` verification and carry the expected Developer ID team identity.
- Apple notarization accepted the exported app and DMG. Both stapled tickets validate; Gatekeeper assesses the app as `Notarized Developer ID`.
- Sparkle generated an appcast and ZIP. An independent Ed25519 check verified the archive signature against the public key embedded in the app.
- The clean GitHub Actions build and test run [36305799671](https://github.com/kzahel/lid-awake/actions/runs/36305799671) passed.
- Exported only the Developer ID Application identity from the login Keychain into a new PKCS#12 archive. A fresh temporary Keychain imported that archive, reported one valid Developer ID identity, and signed and verified a test executable. The tested archive and its randomly generated password are stored as GitHub Actions repository secrets; the temporary archive and password were removed locally.
- The earlier Mac Tart diagnosis stopped too soon: the VM was suspended, and a direct platform command lacked the private target binding supplied by the common `machine-control` CLI. After resuming through the common CLI, guest administration and the resident worked. `maintenance repair --profile development` refreshed an older resident; `target doctor` then reported ready with an unlocked desktop, working Accessibility, capture, and input.
- Installed the notarized local DMG in the macOS 26.2 VM. Gatekeeper accepted it as `Notarized Developer ID`, and strict code-signature verification passed. VM interaction exposed a real app startup bug: the process ran without creating its menu bar item. An explicit nibless AppKit entry point fixed it; the signed replacement displays the menu, duration choices, helper setup, and update controls.
- Helper registration reached macOS's Login Items approval switch and administrator sheet. The testbed's one-shot automated credential entry was rejected. The user then entered the same prepared-image default password directly in the Tart window; macOS accepted it and enabled Lid Awake's background item. This identifies the automated authorization-sheet input path, rather than the saved credential, as the problem. No password reset was needed.
- GitHub Actions [v0.0.1](https://github.com/kzahel/lid-awake/releases/tag/v0.0.1) and [v0.0.2](https://github.com/kzahel/lid-awake/releases/tag/v0.0.2) prereleases completed the signed, notarized CI pipeline. The VM installed the published `v0.0.1` DMG; Gatekeeper accepted the installed app. Independently verified the published `v0.0.1` and `v0.0.2` Sparkle ZIP signatures against the embedded public key.
- The installed `v0.0.1` app crashed after about 4½ minutes while its helper was unapproved. Its VM crash report shows a main-thread timer callback in `HelperClient.proxy(onError:)`. The fix confines XPC connection invalidation to the main thread and sends heartbeats only during an active session. A signed replacement stayed running in the same VM for more than eight minutes with the helper unapproved, no new crash report, and `SleepDisabled = No`.
- GitHub Actions [v0.0.3](https://github.com/kzahel/lid-awake/releases/tag/v0.0.3) built, signed, and notarized the fix. After reinstalling the published `v0.0.1` DMG in the VM, **Check for Updates** offered `0.0.3`. Sparkle downloaded it, **Install and Relaunch** replaced the app, and a new `0.0.3` process appeared. The installed build number is `3`; Gatekeeper still reports `Notarized Developer ID`, strict code-signature verification passes, the menu bar is present, and `SleepDisabled = No`.
- A root-only helper integration harness ran in the same VM with a separate test marker. It verified `enable` sets `SleepDisabled = Yes`, `disable` restores `No`, a fresh helper instance detects an abandoned marker and restores `No`, and the no-heartbeat watchdog restores `No` after its 90-second limit. The wrapper's exit trap independently restored normal sleep, and the test marker was absent afterward. This tests helper logic directly, not the signed app's XPC/SMAppService approval path.
- After the user's one-time Login Items approval, launchd reported `system/com.kzahel.lidawake.helper` running from the installed `0.0.3` app. The app's **Keep Awake** action set `SleepDisabled = Yes`, and **Restore Normal Sleep** returned it to `No`, with no further password prompt. Quitting during a second active session immediately restored `No`. In a third active session, force-killing the app left `Yes` immediately after termination; the helper's no-heartbeat watchdog restored `No` within 90 seconds. These checks exercise the signed app, XPC connection, approved privileged helper, and actual system power setting together.
- On a physical MacBook with the published `0.0.3` prerelease installed, the user enabled Lid Awake and closed the lid. At 2026-09-27 10:35 UTC, the Mac remained reachable through the active remote agent session. I/O Registry reported `AppleClamshellState = Yes` and `SleepDisabled = Yes`; both the installed app and its version-3 system helper were running. The app held its named `Lid Awake session heartbeat` power assertion. The user later reopened the lid and reported that the Mac stayed awake throughout. At 11:38 UTC, I/O Registry reported `AppleClamshellState = No` and `SleepDisabled = Yes`, with the app and helper still running. This establishes a roughly one-hour physical closed-lid session with remote continuity. Restoration was not observed as part of this particular session; a later `0.0.4` on/off test confirmed restoration on the same Mac.
- The user reported that the `0.0.3` menu icon disappeared in dark mode with a black wallpaper. A narrow screenshot of the physical Mac's black menu bar showed an empty status-item slot even though Accessibility exposed `Lid Awake on`. In the VM, the `0.0.3` icon likewise disappeared while active against a black wallpaper. The new icon draws an opaque neutral badge with a white laptop when off and an orange badge with a black laptop when sleep is disabled, without template tinting. A Debug build remained visible against both a light menu bar and a black one. GitHub Actions [v0.0.4](https://github.com/kzahel/lid-awake/releases/tag/v0.0.4) signed and notarized the fix. Sparkle upgraded the VM's installed `0.0.3` to `0.0.4` after helper approval; Gatekeeper reported `Notarized Developer ID`, strict code-signature verification passed, both icon states were visible against black, and the helper still toggled `SleepDisabled` from `No` to `Yes` and back without another password prompt.

Its installed bundle reports build 4, Gatekeeper accepts it as `Notarized Developer ID`, and strict code-signature verification passes. Narrow screenshots of the same black menu-bar slot show the neutral badge in the off state and the orange badge in the active state. A brief physical on/off test set `SleepDisabled = Yes` and restored `No` through the app, without another administrator prompt.
